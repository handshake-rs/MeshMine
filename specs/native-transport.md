# Native overlay transport profile

Status date: 2026-07-18. This is the implemented local research transport for MM-0001 §16, not evidence of a public multi-operator deployment.

## Security boundary

The `meshmine-network` crate runs the overlay over QUIC. The client pins one of at most eight addressed-server TLS certificates, permitting a bounded overlap between retiring and current certificates. After the TLS handshake, the first bidirectional stream performs mutual Ed25519 challenge authentication. Static peers additionally pin the expected authenticated transport public key. Transport keys are independent of the optional economic operator key. A reconnect using the same transport key cannot change its economic-key binding or reset rate, byte-quota, or reputation state.

Each later gossip message or request uses a separate bidirectional stream. Every application frame has a fixed-width little-endian length prefix and is rejected before allocation when it exceeds its configured bound. Authentication and stream processing have absolute timeouts. QUIC idle time, concurrent streams, total connections, gossip sizes, per-topic rates, pending validation bytes, parent-fetch depth, seen/orphan caches, response sizes, and per-peer response bytes are bounded.

Synchronous gossip-validation and response-loading callbacks run through bounded `spawn_blocking` gates rather than on a Tokio runtime worker. Fast-path, accounting, availability, and settlement topics have separately reserved callback capacity under one global ceiling, so a blocked settlement callback cannot consume fast-path permits. Live forwarding likewise has one bounded queue per lane, and each peer reserves an independent in-flight QUIC permit per lane. Replay uses the same object-based send path one item at a time; metadata and outbox locks are released before network I/O, and the ACK write re-resolves the current object locator after the send. A settlement send or replay batch therefore cannot hold a common send lock needed by fast-path traffic, while compaction cannot turn a stale carried sequence into an ACK for another object. Application actor isolation, per-lane metrics/wakeup, and the complete job/winner broadcaster remain open as specified in `latency-lanes-and-fast-path.md`. Gossip validation owns its pending token through callback completion even if the waiting stream is cancelled, and callback panic releases that token. Tokens bind the object ID, authenticating peer, and a monotonic generation, so an expired callback cannot finish or penalize a replacement validation for the same object. A duplicate while validation is pending is rejected. Once validation has completed, an exact validly transport-signed retry of that accepted object receives success without re-running the application callback; the retry therefore cannot replace accepted application state.

Gossip has two signatures and two validation stages:

1. the authenticated transport key signs the topic, object ID, parent metadata, and full payload;
2. the application performs complete object-specific validation and the durable write before the object enters the seen set.

A transport signature is never treated as a protocol-object signature. Body packages and shards are available only through request/response, never unrestricted gossip.

## Runnable service

`meshmine-node overlay-init` creates a persistent Ed25519 transport seed, self-signed QUIC certificate/key pair, and redb state. Secret files are created mode `0600` on Unix and startup rejects group/world-accessible secret files. Initialization is idempotent and does not rotate existing keys. Before listening, `overlay-serve` performs a record-count/size-bounded namespace scan and revalidates every stored operator signature, canonical storage key, network binding, and response size. `overlay-audit` exposes the same fail-closed recovery check without opening a socket. `overlay-observe` adds a bounded, deterministic JSON evidence snapshot for local operations and explorer ingestion. With `--observability-listen`, the daemon serves the same schema through a supervised loopback-only HTTP listener; blocking scans cannot stall QUIC, and the endpoint is GET-only with bounded headers, output, and I/O time. Exact metrics and the unavailable-evidence boundary are defined in `observability.md`.

The standalone `overlay-serve` application always admits `OperatorRecordV2` only after its canonical ID and operator signature pass. Parent gossip is fail-closed by default. It can be enabled only by supplying both `--hsd-cli` and `--settlement-roster`; then each `SessionParentCertificateV2` requires canonical decoding, the configured static committee threshold, a participant-local canonical header/height/time/chainwork check through unmodified `hsd`, and an immutable sequence/previous-ID extension of the crash-safe local head. Every non-research `hsd-cli` consumer, including the one-shot role and HNS-sync commands, requires an absolute canonical regular executable. On Unix it descriptor-traverses every ancestor with `openat`/`O_NOFOLLOW`, rejects non-sticky group/world-writable ancestors and group/world-writable leaves, and requires effective-user or root ownership for the executable leaf. Startup binds the path, device/inode, owner/mode, size, timestamps, and BLAKE2b digest. Immediately before every query it repeats that traversal and identity check, then spawns the exact reopened inode through an inherited descriptor, so a pathname replacement cannot redirect the invocation. JavaScript body/payment adapter commands similarly require an absolute canonical effective-user/root-owned `hsd` source directory with no group/other-writable leaf or non-sticky writable ancestor; a non-writable ancestor need not share the leaf owner. They re-attest its descriptor identity immediately before every adapter spawn and pass that exact directory through an inherited descriptor path. This source check does not hash or recursively pin the imported descendants: the Node launcher still imports a mutable tree, and neither that tree nor the Node runtime has a full artifact/content commitment. Those remain external deployment controls. The effective service user and root can therefore still modify an owner-writable executable or source tree and remain trusted deployment principals.

The immutable parent-certificate journal is audit evidence, not proof that a certificate won admission. Head advancement, a network/sequence/object-bound accepted-parent marker, and a versioned per-network canonical sequence binding commit in one conditional batch. Concurrent valid siblings may both remain as signed journal evidence, but only the head winner receives the marker and sequence binding and is eligible for gossip publication or legacy migration. Canonical bindings for legacy state are built by a CAS-guarded, page/byte/per-startup-work-bounded migration that follows only the accepted head's signed predecessor links, then validates a contiguous sequence-zero-to-head index before service becomes ready. An HNS disconnect atomically marks the directly orphaned accepted certificate and every accepted descendant in its overlay suffix, deletes those exact sequence bindings, and rewinds the head to the last unmarked predecessor. The historical journal and acceptance markers remain audit evidence; a canonical replacement may reuse the orphan's sequence and atomically bind its new object ID. This is also the dependency-safe sender behavior: a configured peer that missed the orphan receives the replacement and its successor, rather than an undeliverable successor whose previous ID was suppressed. Startup repairs an interrupted legacy reorg rewind, walks the record-count-bounded signed predecessor chain, and repairs missing acceptance markers only for the surviving head chain, so a losing sibling cannot become authoritative during recovery. Unlinked certificates are rejected before launching the oracle process; oracle output is capped at 64 KiB and each call at five seconds. Startup rechecks the head and its signed evidence before listening. This sequence index is only the bounded-history foundation: current head recovery still walks back to sequence zero, block/session discovery and one-shot reorg planning still scan retained history, and no reversible checkpoint or resumable deep-reorg fence exists yet. The first locally accepted certificate must be sequence zero, so a newly enrolled node still needs the complete retained certificate chain through a separate import/inventory workflow; a bounded parent checkpoint protocol is not yet defined.

Parent admission conditions the exact `(network, height, block_hash)` MMDB tombstone absent in the same head/acceptance/index transaction. A candidate that passed the local oracle before a concurrent Disconnect therefore cannot resurrect stale canonical state. This per-block admission fence does not supply the still-missing reversible checkpoint or resumable deep-reorg repair fence.

Share gossip is separately fail-closed. It is enabled only when parent admission is active and both `--mask-roster` and `--availability-roster` are supplied. Before serving, the node reconstructs bounded per-session DAGs from its immutable accepted-share journal and checks that every accepted object has the exact durable work-key mapping. For every incoming `ShareV2`, it loads the assignment, mask session, parent certificate, body package and validation evidence, erasure descriptor, availability certificate, and payout bucket by content ID. It then performs the complete protocol linkage, operator signatures, committee thresholds, observation window, payout activation, capture-profile derivation, HNS share hash/target, and participant-local parent-oracle checks. Invalid signatures and proofs are rejected before invoking the more expensive local `hsd` header oracle.

First credit is reserved durably by `work_key` before the validated share gossip is acknowledged. The first observation time is also written immutably. A second correctly signed gossip wrapper for the same physical work is rejected. If the process stops between the work reservation and share write, the exact original share can safely retry; a distinct wrapper cannot take over the reservation. The in-memory DAG is published only after all immutable evidence succeeds. At restart the daemon uses the stored observation rather than the new wall time, replays every share's complete signatures/linkage/proof, caches the expensive parent result by certificate, and only then exposes the reconstructed DAG. A share becomes authoritatively accepted for payout only through the certified receipt path below.

The static roster file is deliberately explicit research configuration:

```json
{
  "protocol_version": 2,
  "network_id": 2,
  "role": "settlement",
  "epoch": 0,
  "threshold": 2,
  "members": ["32_BYTE_ED25519_KEY_HEX", "32_BYTE_ED25519_KEY_HEX"]
}
```

The same schema is used for `mask` and `availability` files by changing `role`, epoch, threshold, and members. `settlement-roster.example.json` is schema-valid illustrative input only; its placeholder keys are not a trusted committee.

`share-context-import` is the explicit static-profile context boundary. It accepts canonical binary parent, body, descriptor, body-certificate, mask-session, assignment, and payout-bucket objects. Before writing anything, it checks every version/network/content ID and cross-link; operator and all three committee signature sets; the session schedule and capture profile; descriptor parameters and exact canonical body size; payout activation; the participant-local canonical parent; and the full candidate block through the running `hsd` RPC `verifyblock` path with only PoW disabled. The helper streams the raw HNS block on bounded stdin so a near-4-MiB package never enters the process argument list. The production MaskSession write is not an unguarded journal append: it atomically persists the session and increments a per-network inventory generation while conditioning the durable parent-orphan marker, exact height/hash MMDB tombstone, session reorg marker, and session closure row absent. Disconnect preparation and orphan-head rewind snapshot that generation before scanning MaskSession evidence and require its exact bytes at commit. Therefore a session that wins first changes the generation and forces a complete rescan/closure, while an event that wins first leaves the MaskSession journal absent. Only after those checks pass are the exact bytes and local body-validation commitment written immutably.

With `--receipt-roster`, the service also admits `ReceiptBatchV2` and `SessionCloseV2` gossip. A batch must have the configured receipt threshold, extend sequence zero or the exact previous batch, contain canonical sorted entries, preserve cumulative counts/work and Merkle roots, and identify exact locally stored shares, work keys, and credited work. A close must cover that complete receipt chain and have the configured settlement threshold. Once closed, a session cannot accept a later batch. Recovery reconstructs and re-verifies every chain and close before listening; multiple closes or missing share evidence fail startup.

The capped active-receipt path remains separate work: payout-enabled startup still performs historical receipt recovery before loading active receipt admission state. Atomic Disconnect composition does not close that ordering/recovery gate.

The long-running daemon still does not load committee private keys. The bounded `committee-key-init`, `receipt-propose`, `receipt-sign`, and `receipt-assemble` commands provide an operator-driven static receipt workflow using the same state. A proposal is the frozen canonical `ReceiptBatchV2` with an empty certificate. Every signer independently recovers and exactly revalidates active share evidence, checks the parent through its own `hsd`, reconstructs the unsigned cumulative batch, verifies roster membership, and reserves the roster/session/sequence with `DurableSignGuard` before emitting its canonical `SignerSignature`. The assembler sorts and deduplicates entries, verifies the threshold, writes a publication intent, durably admits the certified batch, and creates its static-peer locator before exposing the exact certified file. Proposal, signature, and output artifacts use atomic no-overwrite writes with exact-retry idempotence. Partial signatures are operator-exchanged artifacts, not a new gossip message. The complete workflow and its remaining automation boundary are in `receipt-role.md`.

With `--payout-profile`, the service additionally admits `PayoutSnapshotV2` and `PayoutPlanV2`. The strict profile freezes ticket/output policy, the exact U512 snapshot step and PPLNS window, entropy delay and count, a hard entropy parser bound, and one explicit research prior beacon. Static daemon composition is work-only: service ticket count and allocation must be zero because no durable daemon service-event format exists from which another signer could reproduce service leaves. Snapshot recovery verifies every receipt and close, loads each exact accepted share and signed active payout bucket, reconstructs one complete previous-ID-linked session lane, replays `SnapshotAccumulator` from sequence zero, and requires each unsigned snapshot to equal that exact accumulator output. Arbitrary threshold-signed work windows, anchors, bucket distributions, or service credits therefore fail. Multi-lane snapshot ordering is not frozen and fails closed. A plan must reference a known exact snapshot, use precisely `h + D`, contain exactly `R` hashes and the configured beacon, reproduce the rejection-sampled winners/transcript, and bind every entropy height to the participant's current canonical `hsd` chain. Canonicality results are not retained across queries. After a reorganization, the old plan remains immutable audit evidence while one newly canonical replacement can occupy its sequence. The example profile in `payout-profile.example.json` is illustrative, not a mainnet parameter recommendation.

The settlement library now has a bounded certified recovery checkpoint. Its exact committee policy and eligible Ed25519 threshold are verified, the certified-wrapper hash and unsigned checkpoint ID are sealed under the monotonic `MMCH` head, and persistence is conditioned on an exact `MMSF` source fence. Recovery is O(1) from the head and rejects any live source fence that has advanced past the checkpoint. Online daemon cutover remains disabled: every close, reorg, snapshot, plan, and payment source transaction must advance the same fence atomically, and a bounded migration must install the initial certified head before startup can stop replaying historical evidence.

The `payout-snapshot-propose` and `payout-plan-propose` commands emit those exact frozen objects with empty certificates. `settlement-sign` repeats the complete local validation, checks settlement membership, and durably reserves the signature before emitting a canonical `SignerSignature`; `settlement-assemble` verifies the threshold and performs intent/admission/outbox/output ordering. Snapshot signing permits one object per roster/sequence. Plan signing binds the guard to roster, snapshot, and exact HNS entropy branch, so it cannot double-sign one branch but can remain live when a reorganization makes a different deterministic branch canonical. Partial signatures remain authenticated operator artifacts. See `settlement-role.md`.

`overlay-sync-hns` is the bounded static-profile chain controller. Its first invocation requires an explicit `--from-height` reorganization horizon; later invocations resume from an immutable, contiguous connect/disconnect journal. Repeating the configured horizon is permitted only when it exactly matches the durable first event. Each block is resolved by canonical height before and after body retrieval and decoded by the referenced running `hsd`. A block advances the lowest-payable plan only if its coinbase has exactly one canonical `HNSM` commitment matching the locally certified snapshot/plan and its actual first-work, mandatory claim/airdrop, remaining-work, and service outputs reproduce the deterministic static-profile payout at `hsd`'s subsidy. Non-MeshMine blocks are connected without advancing plan sequence. For a live Disconnect, the raw canonical-payment event, exact per-block MMDB tombstone, earliest parent/session reorg markers, closure rows, accepted-head rewind, and exact canonical-sequence (`MMPC`) deletions commit in one conditional redb transaction; the same ordered batch is atomic under the memory store. Exact existing marker and tombstone bytes are CAS conditions, and the staged value is `min(existing, new)`, so losing a race retries the entire transition without moving the earliest sequence forward. Startup repair decodes and validates the complete ordered raw event chain before any reorg write, aggregates all Disconnects by `(height, block_hash)` with the earliest event sequence, and then scans parent and MaskSession journal evidence once per complete CAS attempt. A malformed or gapped raw chain therefore produces no derived reorg writes. Raw repair never fabricates missing payout-admission evidence; legacy paid Connect/Disconnect state is replayed only from retained valid evidence. Historical orphan parent/share/plan evidence is retained so audit and payment replay do not depend on current canonicality. `--maximum-events` bounds each invocation and reports a partial status when more work remains.

Only post-atomic close provenance is promotable: the normal-first proof (`MMNP`) namespace is v4 with the `MMN4` encoding, active-share migration uses `MMA4`, and the ordered `MMCI` migration is v5 with `MMC5`. Pre-atomic `MMNP` v3/`MMA3`/migration-v4 state is ignored or reset and must be revalidated from retained source evidence. These schema changes deliberately do not claim completion of the lifetime-bounded parent-repair/deep-reorg fence described above, the separate active-receipt recovery/composition work, or atomic payout-accumulator checkpoint integration. The public multi-operator, independent-audit, hardware, committee, and operational release gates remain external.

`overlay-serve` composes the same controller when `--hns-sync-source` is present. It completes one bounded reconciliation before opening the QUIC socket, then repeats at the configured interval in a blocking-worker boundary so RPC latency cannot stall QUIC. Sync flags without the source are rejected; payout/roster/`hsd` admission is mandatory; intervals and per-pass events are bounded. An oracle failure, a reorg deeper than the durable horizon, or catch-up exceeding the per-pass bound stops the service fail-closed. The configured horizon can remain unchanged across restarts and is checked against the immutable log. A one-shot catch-up can be used before restart when the service was offline for more blocks than its configured per-pass bound.

With `--peer-config`, `overlay-serve` also supervises one reconnect loop for each of at most 64 explicitly configured peers. The file binds protocol/network, socket address, TLS name, one to eight trusted certificate files, and the expected 32-byte transport public key. Peer identities and addressed server names must be unique; certificate files and the forwarding queues are bounded. `forward_queue` is the capacity of each of four isolated queues (fast path, accounting, availability, and settlement), not a shared aggregate capacity. Relative certificate paths resolve next to the configuration file. Backoff starts between 100 ms and 60 seconds, doubles to a configured ceiling no greater than five minutes, and QUIC keepalive is derived from the bounded idle timeout. A malformed local TLS configuration stops the service; unreachable, wrong-certificate, or wrong-transport-key endpoints remain disconnected and receive no objects. Replay defaults to a five-second interval with at most 256 objects and 16 MiB per peer pass; configuration can select 1--4,096 objects, 1--64 MiB, and an interval from one second to five minutes.

Every supported object that passes full application validation and durable admission is offered to the bounded live-forwarding queue for its protocol lane and represented by a durable sequence locator to its authoritative journal bytes. A saturated settlement lane therefore cannot consume fast-path queue capacity, callback workers, or a peer fast-path in-flight permit. The supported set is operator records, parent certificates, shares, receipt batches, session closes, payout snapshots, and payout plans; disabled contextual topics are not advertised merely because opaque bytes exist. Before validation begins, the service writes a canonical publication intent keyed by topic, object ID, direct source, and a domain-separated hash of the exact signed wrapper. Rejection clears only that wrapper's intent. Successful admission clears it only after the durable locator and source mapping exist. Thus a stop before the authoritative write is distinguishable from a stop after admission but before locator publication, while two signature wrappers with the same unsigned object ID cannot erase one another's recovery evidence. Connected authenticated peers receive live objects concurrently, except for the direct source transport key, and a slow peer is bounded by the QUIC idle timeout. The direct-source mapping is durable even when the live queue is full, so an object is never echoed to the peer that supplied it. Queue pressure or disconnection is reported and does not revoke the source object's completed durable admission.

Each configured peer has a compact durable acknowledgment bitmap and rotating replay cursor. At startup, a bounded recovery pass first repairs locator/index/counter crash gaps, then resolves publication intents against the exact authoritative wrapper. Missing or mismatched payloads clear harmless pre-admission intents; an exact admitted payload publishes its locator and preserves its source; an already published locator is idempotent. Parent payload lookup additionally requires the accepted-parent marker, so an intent for a journaled losing sibling is cleared rather than published. Parent locators in a durably orphaned suffix and share locators whose session is durably reorg-closed are global local-delivery tombstones: intent recovery, first migration, live forwarding, source settlement, and replay skip them. The rotating cursor may advance, but the peer acknowledgment bitmap is never changed merely because of this local suppression, and a remote rejection alone can never create a tombstone. A canonical bitmap migrates other legacy history only once for each enabled topic group, in dependency order. Contextual groups that are disabled on an earlier run remain eligible for their later first migration, but a completed group is not scanned again and therefore cannot resurrect subsequently retired history. Periodic bounded passes load payloads from their authoritative namespaces and fairly retry unacknowledged objects, healing disconnection, queue pressure, and process restart without allowing a permanently rejected early object to starve later entries. A successful remote acknowledgment is then recorded locally; an interruption after the remote acknowledgment but before that local write can produce a completed-object retry. The receiver acknowledges that validly signed retry without re-running application admission, but sender-side delivery remains at-least-once rather than exactly-once because the local acknowledgment write may still be repeated. Malformed intent, migration, compaction, locator, index, source, counter, tombstone, or configured-peer acknowledgment state fails startup. The existing signed Core v2 gossip frame is reused; no new wire object was invented.

Once a contiguous prefix is settled for every currently configured peer, the supervisor compacts it. A tombstoned locator also qualifies its position in that prefix without manufacturing any peer ACK; a prefix containing one is eligible immediately. Other passes ordinarily batch at least 1,024 objects, while at 75% of the 100,000-object capacity any nonempty settled prefix is eligible. It takes every peer metadata lock in transport-key order, then uses one redb transaction to delete the retired locators/indexes/source mappings, rebase the retained locator suffix and every real acknowledgment bitmap to sequence one, reset replay cursors, update the counter, and advance a canonical cumulative compaction record. Network sends do not hold those locks. A send that finishes across the transition resolves the object's current index again before recording settlement, so it cannot acknowledge a different rebased object. An in-flight publication intent defers the pass. Exact authoritative gossip whose locator was retired is accepted as existing protocol evidence but suppressed as a delivery duplicate; a different signed wrapper cannot inherit that classification. The same ordered batch operation is atomic in the memory model and redb backend, so restart observes either complete pre-compaction or complete post-compaction metadata. Schema-v3 observability reports active local tombstones separately from peer-settled and pending counts.

This is bounded sender-side durable catch-up with compaction, not remote inventory reconciliation. Retirement proves only that every peer configured at that pass was locally recorded as settled; it does not prove continued remote retention. Removing a peer from trusted configuration removes it from future retirement quorum. A newly added or re-added peer receives the retained suffix and future objects, not already retired history; operators need an explicit import/inventory workflow for that history. The outbox is capped at 100,000 active records; reaching the cap while no settled prefix is available, or outrunning the periodic compactor with a burst, deliberately stops service instead of silently losing delivery evidence. Opaque remote rejections remain unacknowledged and are retried fairly, so they can prevent prefix retirement. Body packages and shards remain request/response only and are not pushed by replay. Schema-v2 local observability exposes exact durable locator/capacity/topic/source counts, pending publication-intent count, migrated topic groups, cumulative retired-object count, compaction generation, and each configured peer's settled/pending bitmap state, but it has no durable retry/rejection counters or live connection-health evidence. There is no discovery, routing, NAT traversal, certificate authority, revocation feed, or automatic certificate rotation. Operators must distribute peer configuration and overlapping pins through a trusted operational channel, remove retired pins after the deployment window, and use explicit fetch/import workflows for request/response bodies and any evidence outside the supported gossip topics.

`MaskOpening` remains fail-closed. MM-0001 specifies timed-opening behavior and a suggested topic, but not a canonical opening-share payload/object ID, setup-transcript distribution object, or signed close-intent that fixes the accepted-share boundary before shares are broadcast. `SessionCloseV2` instead contains the post-opening transcript root. `OPEN-QUESTIONS.md` records this gap; the daemon does not silently create a conflicting Core object.

This import mechanism is a manual research-profile snapshot, not a dynamic context-distribution protocol. Receipt-batch and strict work-only single-lane payout threshold production have bounded one-shot static workflows, but automatic proposal/signature exchange, timer-driven batching, session creation and close production, mask opening, service-credit production, multi-lane payout ordering, and dynamic rosters remain outside the standalone service. Continuous canonical reconciliation, block-payment writes, and rollback are supervised locally, but operators must still choose a horizon that covers every active parent and entropy window.

All seven §16 request protocols are transported. `overlay-put-response` places an immutable, network-scoped bounded response in the durable store; `overlay-fetch` retrieves it from an authenticated peer. This permits local body-shard and transcript transport testing without claiming that arbitrary imported bytes were protocol-certified.

## Local operation

Create distinct identities for the server and client:

```sh
cargo run --locked -p meshmine-node -- overlay-init --dir /tmp/mm-server --server-name localhost
cargo run --locked -p meshmine-node -- overlay-init --dir /tmp/mm-client
```

Import a response and start the server:

```sh
cargo run --locked -p meshmine-node -- overlay-put-response \
  --dir /tmp/mm-server --network-id 2 --protocol body-shard \
  --id OBJECT_ID_HEX --shard-index 0 --file /path/to/shard.bin

cargo run --locked -p meshmine-node -- overlay-serve \
  --dir /tmp/mm-server --listen 127.0.0.1:9443 --network-id 2 \
  --peer-config /absolute/path/static-peers.json
```

`static-peers.example.json` documents the bounded schema. Replace the
illustrative zero transport key with the peer's `overlay-init` output and
replace both certificate paths with files delivered over a trusted channel.
Listing both retiring and current certificates creates a staged rotation
window; the server still presents only its locally configured certificate.

For a share-validating static profile, import the complete context and start
the endpoint with the same roster/oracle configuration:

```sh
cargo run --locked -p meshmine-node -- share-context-import \
  --dir /tmp/mm-server --network-id 2 \
  --hsd-cli /path/to/hsd-cli --hsd-source /path/to/hsd \
  --settlement-roster /path/to/settlement.json \
  --mask-roster /path/to/mask.json \
  --availability-roster /path/to/availability.json \
  --parent /path/to/parent.bin --body /path/to/body.bin \
  --descriptor /path/to/descriptor.bin \
  --body-certificate /path/to/body-certificate.bin \
  --session /path/to/session.bin --assignment /path/to/assignment.bin \
  --payout-bucket /path/to/payout-bucket.bin

cargo run --locked -p meshmine-node -- overlay-serve \
  --dir /tmp/mm-server --listen 127.0.0.1:9443 --network-id 2 \
  --hsd-cli /path/to/hsd-cli \
  --settlement-roster /path/to/settlement.json \
  --mask-roster /path/to/mask.json \
  --availability-roster /path/to/availability.json \
  --receipt-roster /path/to/receipt.json \
  --payout-profile specs/payout-profile.example.json \
  --hns-sync-source /path/to/hsd --hns-sync-from-height HEIGHT \
  --hns-sync-interval-ms 10000 --hns-sync-maximum-events 256

cargo run --locked -p meshmine-node -- overlay-sync-hns \
  --dir /tmp/mm-server --network-id 2 \
  --hsd-cli /path/to/hsd-cli --hsd-source /path/to/hsd \
  --settlement-roster /path/to/settlement.json \
  --payout-profile specs/payout-profile.example.json \
  --from-height HEIGHT --maximum-events 256
```

Fetch it from another terminal:

```sh
cargo run --locked -p meshmine-node -- overlay-fetch \
  --dir /tmp/mm-client --remote 127.0.0.1:9443 \
  --server-name localhost --trusted-cert /tmp/mm-server/quic-cert.der \
  --network-id 2 --protocol body-shard --id OBJECT_ID_HEX \
  --shard-index 0 --out /tmp/fetched-shard.bin
```

Certificate files and expected transport keys must be distributed over a trusted channel. The local service supports only operator-managed staged pin overlap; it does not provide discovery, automatic rotation, revocation, NAT traversal, peer discovery, or DDoS infrastructure.

## Automated evidence and remaining boundary

Loopback tests cover mutual authentication, separate economic and transport identities, wrong-certificate rejection, both sides of a two-certificate rotation window, certificate-count/configuration bounds, expected transport-key pinning, tampered gossip rejection, full application validation before admission, completed-retry acknowledgment without a second callback, pending-duplicate rejection, generation-bound stale-token rejection, blocking-callback runtime responsiveness and cancellation, response quotas, reconnect quota preservation, immutable storage, secret permissions, identity reuse, malformed durable-record rejection, threshold-signed and sequence-linked parent admission, accepted-parent marker recovery, and a concurrent sibling race that never publishes the losing audit candidate. A supervised static peer durably forwards a correctly signed operator record, detects a server shutdown, reconnects after the same server address restarts, forwards a second object, and shuts down cleanly. Durable-catch-up tests fill the live queue, admit objects while offline, restart the source process, repair a legacy/crash-gap object, and deliver all four through bounded replay. They also cover every publication crash phase, exact-wrapper intent isolation, incremental and idempotent topic migration, non-replay of migrated untracked history, source suppression after a dropped live event, compact acknowledgment persistence, rotating retry fairness, malformed intent/migration/compaction/acknowledgment rejection, every composed contextual gossip topic in dependency order, and supervisor termination on outbox publication failure. Reorg delivery tests cover accepted-suffix head rewind, same-sequence canonical replacement, an offline peer that missed the orphan but accepts the replacement and successor, parent/share tombstone replay suppression without false ACK bits, restart, and contiguous prompt compaction. Atomic Disconnect tests additionally cover one raw-event scan across one versus many Disconnects and one parent plus one MaskSession evidence scan per CAS attempt, earliest-sequence marker preservation after forced CAS loss, malformed/gapped raw history producing zero derived writes, legacy paid-Connect rollback without payout normalization, both exact orderings against normal close and MaskSession import, and a parent that passes oracle validation before losing admission to MMDB. General compaction tests cover atomic cross-namespace batches in both storage backends, in-flight intent exclusion, two-peer prefix intersection, suffix and ACK rebasing, stale queued acknowledgments, retired exact/alternate wrappers, restart, repeated capacity reuse, high-water eligibility, and an actual supervised 1,024-object production pass. Receipt-role tests cover deterministic bounded proposal construction, two independently valid proposals for one sequence, signer eligibility, exact retry, durable conflicting-object rejection across restart, threshold assembly, atomic artifact writes and secret permissions, plus recovery from a crash between certified receipt persistence and outbox locator creation.
